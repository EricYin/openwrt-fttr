# SCTY / COMHEART TY-FS803G：授权与原生桥接案例（脱敏）

历史窗口：2026-11-06，MGS.V1.0.0.0 固件、HM2004 miniOLT。目标用 `<ONU_A>`，
主猫和管理端点用 `<OLT_HOST>`、`<ACS_URL>`；身份、凭据、私有路径和原始包不收录。
当前源码复核基于 `cb1a62d`，终端验收记录为 `1a62b0f`；换固件/FPGA 版本需重新验证。
源码提交当时目录名为 `h3c-fttr-tools`；下列源码路径按当前 `fttr-tools/` 布局书写。

## 1. 结果与边界先行

- 原生桥接 DHCP、路由、网关/公网 ICMP、DNS 与 HTTP 下载通过；用户确认 LAN 和
  Wi-Fi 终端均正常上网。没有保留临时地址、host route、桥成员或暂停管理授权线程。
- 三台既有 ONU 同窗正常双向通信。约 29 秒诊断窗口 LoB/BIP、Ethernet CRC、drift
  增量为零；全局 BCH 仍有增量，来源未确认，不能写成“全部硬件无错误”。
- CWMP 仍 `waiting_inform`，真实 Inform/RPC 未通过；联网成功不升级为完整管理支持。
  满速、多台同型号扩展性、长时间和重复重启验收也不由短时检查替代。

## 2. 为什么不能只继续堆 OMCI 属性

起点是 O5、桥/GEM/EVTO 回读通过，但主猫目标 RX 不增长。排查逐层更新假设：

| 证据 | 得到的结论与限制 |
| --- | --- |
| 子猫 WAN 有活动，TM 队列持续积压，业务 GEM TX 不变 | 流量已进入队列，不能继续只怪 WAN 分类；全局 GEM TX 增长包含 OMCC |
| 当前 Root TM 存在、硬件 Alloc-ID/T-CONT/GEM 绑定一致 | 历史“找不到 Root TM”日志不是当前根因证据 |
| 实际 BWmap 有目标 Alloc-ID，但捕获到的窗口只有两字节 DBRu-only | 修正“完全没有授权”的早期推断；稀疏样本不证明所有帧都没有长授权 |
| 健康 ONU 在定向负载下能取得长授权，目标积压仍不出队 | 缩小到目标授权/反馈路径，尚未取得线上 DBRu 或 FPGA 解析结果 |
| 给业务窗口有界增加长度，实际窗口变长、队列开始出队 | 授权控制确实生效，但主猫持续接收和 DHCP 仍未通过 |
| 同窗主猫 LoB 停止增长，BIP/BCH 快速增长 | 故障点已转移，不能把“队列出队”写成通信成功 |
| 有界暂停管理窗口后有真实 DHCP，恢复后错误增长恢复 | 管理/业务共存路径成为重要变量；不能永久停管理授权作为修复 |
| 管理窗口增加后，OMCI 活体与业务可共存、实际 DORA 出现 | 仍须验证原生 IP 路径与终端，DORA 不是完整验收 |

G.984.3（01/2014）8.1.3.6、8.2 允许 DBRu-only 两字节分配，StartTime 不含 PLOu；
同 ONU 连续分配可属于同一突发。本案没有证明最终的 DBRu 接收/解析或突发处理机制，
也没有证明必须使用某种私有协议。不要把有效兼容策略误写为完整硬件根因。

## 3. 固件逆向怎样帮助排除错误假设

对运行中的库/模块与提取固件核验 hash，区分 ARM32 子猫与 AArch64 主猫，以及
动态 ELF 地址与 ET_REL 节相对偏移。原始固件保持只读，脚本与脱敏过程单独保存。

- `rutGpon_isAllocIdInitValue` 路径显示 `ffff` 是跨所观察模式的初始值，`00ff` 有
  模式条件；不能笼统声称 reset 255 必然重建 TM。现场重置 Alloc-ID 后仍不通，
  所以不把该静态发现记为最终修复。
- Queue scheduler pointer 为零有合法处理路径；正在使用的 ME 277 从 `0000` 强写
  `8000` 被拒，串口给出对应参数错误。移除无证据的写入，而非继续把实体编号当作
  必须的指针值。schema 索引/掩码与实际回读一并核查。
- 标准下发迁移到生成 schema 时，ME 277 的 RelatedPort 与 scheduler pointer、
  ME 11 的自动检测与 admin 属性不能混用。编码还须保留旧请求的零填充语义，避免
  上游默认值改变线上的 CREATE；用独立字节夹具校验，而非仅对照新实现自身。
  严格/宽容 CREATE 策略分别保留，非法输入在探测或删除资源之前拒绝。
- 缺 option125 的 DHCP 分支继续处理 Offer/ACK；不能从该日志断言必须伪造运营商选项。
- `ssk_ty` 的 FTTR 角色把 DHCP 交给 br0 特殊处理；`libcms_core.so` 的内部 WAN 判断
  检查桥接、INTERNET、未标记 VLAN。它解释了配置模式为何需要独立核验，但不授权
  适配器静默重写用户 WAN。
- 原厂 HM2004 `moltdbg` 中的已验证寄存器映射封装为只读 `fpga-diag`。另一个程序
  中发现的间接寄存器表未证明适用于当前 FPGA，未据此盲写。

逆向证据至少记录文件 hash、运行版本匹配、函数/字段位置与证据等级；不能把其他
rootfs 的地址、静态默认值或厂商日志中的“成功”当作当前硬件状态。

## 4. 第二层问题：人为 Routed 与出厂桥接不同

用户后来确认 INTERNET 曾被改为 Routed。此时 DHCP 将地址/默认路由放在 br0，
VEIP 未形成可通信的原生路径。临时 VEIP 别名与定向路由能成功 ping 公网，只证明
光侧/IP 路径可以打通；测试结束恢复，未作为最终方案。

单独 brctl 加端口、放行桥过滤、运行时改 Bridged 均未恢复原生通信；Connected
只是页面状态。部分 MAC 改写试验因工具不支持未执行，不能写成“MAC 假设已排除”。

用户明确决定恢复出厂并开启 Telnet 后，重新发现到：INTERNET 是连接 1、接口
`veip0.1`、IP_Bridged、VLAN -1，自动接入 br0，原生 DHCP 和默认路由存在。
旧连接 2 / `veip0.2` 假设失效；没有再次执行旧实例的写入脚本。
这不是所有设备接入都必须重置的证据，也不是适配器执行恢复出厂。

## 5. 从试验进入正式资源生命周期

当前型号策略为业务窗口 1300 字节、管理窗口 60 字节；现场控制字分别为
`0x11000514`、`0x1100003c`。这是该型号/固件与当前 FPGA 的实测兼容策略，
**不是通用推荐值，也不提供抄写到其他 ONU 的寄存器命令**。
低位长度行为由实际 BWmap 验证，未知位的完整定义仍未还原。过大的候选曾挤占
OMCC；固定窗口消耗共享带宽，不表示吞吐保证或多台规模化已通过。

- 型号策略：`fttr-tools/src/src/devices/scty/ty_fs803g/service.rs`。
- 公共机制：`fttr-tools/src/src/pon_engine/omci/platform/leases.rs`。配置失败恢复，
  成功后保留已归属的 Alloc-ID/窗口，临时 OMCC lease 不覆盖它们，离线清理清空缓存。
  此缓存属于同一 daemon 进程，外部进程不能假定共享所有权。
- 最终 ONU-G GET 成功才提交 lease；移除所有临时试验线程和旧二进制。其他型号未
  套用本型号策略，测试覆盖所有权、保留和清理；型号 feature 关闭仍可编译。

还应核查 MIB 上传是否重复启动、长期占锁阻塞恢复。本轮没有把单型号需求转化为
全局缩短 MIB 超时，也不将长时占锁的观察误写为已经修复的公共调度问题。

## 6. 验收与复查入口

原生通信验证：三轮网关/公网各三次共 18/18；1200 字节网关 100/100、公网 20/20；
DNS 解析和 HTTP 下载成功；双端业务 GEM 增量、LAN/Wi-Fi 用户测试分别记录。
回归为 522 passed、0 failed、5 ignored，动态 musl 构建及无设备 feature 检查通过。

只读入口（先以当前身份确认槽位，示例检查所有槽位，不包含写入）：

```sh
fttrctl fpga-diag all --samples 10 --interval-ms 500 --json
```

LoB/BIP 是 16 位模差；高增长下多次回绕会漏计。采样带 daemon/注册连续性，但不
保证没有硬件清零，离线模式缺少连续性上下文。BWmap、业务实包和端到端响应仍需
另取证，计数不能替代它们。

当前可复核的寄存器映射与限制见 [`fpga_diag.rs`](../../../../fttr-tools/src/src/fpga_diag.rs)，
CLI 入口见 [`fpga_diag_cli.rs`](../../../../fttr-tools/src/src/fpga_diag_cli.rs)；实现内记录
原厂 `moltdbg` SHA-256、字段/地址映射和非原子读取、回绕/重置及槽位身份限制。历史
现场汇总位于本机忽略的 `EVIDENCE/TY-FS803G-bridge-validation-2026-11-06.md`，不随仓库分发。

不属于当前 refs、GitHub 链接也不可用；故不将其作为当前可访问证据链接。部署与代码阶段
对应 `6749c9f`、`cb1a62d`，只读诊断代码对应 `ebbf55d`。
