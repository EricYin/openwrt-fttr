# OMCI 结果码与数据面定位

本参考按 2026-10-28 现场观察整理。结论只描述当时的实现与设备；换固件、换型号或换主猫版本后要重新取证。
路径均相对仓库根目录。

## 1. 先判定拒绝层级

| 层级 | 可接受判据 | 常见误导 |
| --- | --- | --- |
| OMCI 语义 | 失败操作 + 类 + 实例 + 掩码 + 结果码；同类其它实例是否成功 | “返回错误 = 设备不支持该类” |
| 我方配置逻辑 | 选中的实体/实例/指针来自 MIB 还是模板常量 | “标准流程一定通用” |
| 宿主门控 | `fttrN` carrier、健康监控活体节律、内核 `tx_dropped` | “OMCI 通了就该通” |
| 数据面 | 当前窗口内可归属目标的新鲜 GEM 报文 | 累计计数、DHCP 一次成功 |
| 接线/物理 | 环路、风暴、PON 口状态、ONT 侧 UNI 链路 | “设备重启过所以配置是新的” |

先证明层级，再改代码。层级没分清时，任何"修好了"都可能只是换了个失败点。

## 2. 结果码按设备校准

下表是**观察记录**，不是规范映射。规范含义与厂商实现可能不同，必须用本机请求/响应校准。

| 结果码 | 规范/常见含义 | 现场观察 | 处理策略 |
| --- | --- | --- | --- |
| 3 | 参数错误 | ME 268 CREATE 时上行 TM 指针为 0，附带 `mask 0x1000`；某 Lantiq 系 ONT 拒绝用 OMCI 写 ME 262 的 Alloc-ID | 修正参数本身；确实不可写的属性降级为“跳过并记录”，不中断整条 profile |
| 4 | 未知 ME 实例 | 换型/换槽后的探测 | 视为“不存在”，可以创建 |
| 5 | 未知实例/属性 | 写死拓扑的 profile 探测不存在的 T-CONT / UNI / VEIP | 视为“不存在”，可以创建 |
| 7 | 规范里多为 device busy | CREATE 一个**已存在**的 ME 268 时观察到的就是 7 | 不要直接当成功；先用窄掩码确认存在，再决定复用还是删除重建 |
| 9 | 不支持属性掩码 | 同一台 ONT 对**已存在**的 ME 268 做 GET 也回 9 | **绝不能**当成“不存在”；窄掩码二次探测，仍不明确就删除重建 |

由此得到三条硬规则：

1. **探测用最窄的可信掩码**（例如只看标识属性），不要用一个大掩码去判断存在性。
2. **判不准就替换**：删除该实例再按我方定义创建，比"猜测复用"更容易收敛；删除失败也要记录。
3. **CREATE 后读不回可以接受**，但必须在日志里写明 `CREATE_ACCEPTED_WITHOUT_READBACK`，并在验收里降级为"未验证"。

## 3. 报文级定位（OMCI 通道）

- 设备：`molt_omci`。8 字节信封（`type=3`、ONU-ID）之后是基线帧：事务号 2 / 类型 1 / 设备号 1 / 类 2 / 实例 2 / 属性 32，其余为对齐填充（整帧按 56 字节处理）。
- 抓取：

  ```sh
  tcpdump -i molt_omci -XX -nn -c 1600 -w /tmp/omci.pcap     # 一次完整配置周期
  tcpdump -r /tmp/omci.pcap -XX -nn
  ```

- 成对解读：同一事务号的 0x49/0x29（GET）、0x48/0x28（SET）、0x44/0x24（CREATE）、0x4d/0x2e（MIB 上传）。响应体首字节是 `result`；GET result=9 时后四字节是 unsupported/failed mask，SET 失败时同理，CREATE result=3 时携带执行掩码。
- 先看**最后一次成功**的操作，失败点就是它的下一步；不要从头读整个周期。
- MIB 上传很占帧：一次 200+ 条实体的上传会淹没短窗口，抓包要放大 `-c` 或按需过滤。

## 4. 报文级定位（GEM 通道）

- 设备：`fttr0`。外层 VLAN 低 12 位是 GEM 端口（本机约定 `0x100 + ONU ID`），PCP 1 = OMCI，PCP 0 = 业务。
- 判定当前是否真有目标流量：`vlan <0x100+id>, p 0` 且源 MAC 不是 `00/55/aa` 这类本机/占位 MAC。
- **TX 门控证据**：往 `fttrN` 发一帧后，若 `statistics/tx_dropped` 增长而 `fttr0` 上没有对应 VLAN 帧，说明帧在内核层就被丢弃（carrier=0 时会发生），与 OMCI 无关。
- 计数陷阱：`fttr0` 的 rx/tx 计数可能包含非帧单位（本机曾出现每秒数十"包"但抓不到帧），不要用累计计数证明转发。

## 5. 读 ONU 自己的栈日志（能登录 ONU 时）

部分 SFP ONT 可直接登录（Lantiq/华为系参考实现），其 OMCI 守护进程日志能直接给出校验点，例如：

```
[omcid] ME ERR: Can't create "GEM port network CTP" (268) with instance id = 256,
        SBC validation error (mask 0x1000)
[omcid] ME ERR: 256@0 Try to set invalid attribute; attr_mask = 0x0010, inv_attr_mask = 0x007f
[omcid] CORE ERR: Managed Entity instance 268@256 was not found
```

用法边界：
- 这是"ONU 侧自述"，用来形成假设；最终结论仍以本机请求/响应和回读为准。
- 若要隔离"是我方报文错，还是 ONU 校验严"，可在 ONU 自身 MIB 模板里预置一个符合标准的实体（例如带正确上行 TM 指针的 GEM CTP），重启其 OMCI 守护进程后看主猫能否继续走完 profile。这会改变调查对象，必须先记录原状与恢复路径，测完立即还原，并在结论里注明"运行态 MIB 与文件模板是两份状态"。
- 有些实现会在二进制里留下判定语句（如"指针冗余指向 T-CONT 则跳过校验"），可作为验证方向，但不能替代实验。
- 改动 ONU 自身的 MIB 模板/配置属于改变调查对象：先记录原状与恢复路径，测完立即还原。

## 6. 宿主侧门控（本仓库实现）

- `fttrN` carrier 必须由"OMCI 活体"驱动；若要求"先收到 ONU 上行帧"才拉起 carrier，空闲 LAN 会永久死锁（内核丢下行帧，ONU 侧也就没有应答）。业务状态可以另外等 GEM 证据，但端口不能等。
- 健康监控的活体判定不能拿 PLOAM 厂商码去比对 OMCI 的 ONU-G VendorId；两者在真实设备上可以不同，判错会形成 15 秒拆 carrier、30 秒重配的固定节律。
- 指纹日志：`VERIFIED_LINK_ENABLED` → `VERIFIED_LINK_DISABLED ... stale` → `watch lost ONU` 循环出现，先查这两条。

## 7. 接线与风暴

- 环路指纹：内核打印 `received packet on <port> with own address as source address`；目标 `fttrN` 的 tx 包速长期上万；`br-lan` 计数暴涨。
- 机制：广播风暴挤占 OMCC 的小授权窗口，OMCI 采样丢失，carrier 被拆，重配后再次成环，表现为"通了几秒又断"。
- 处置：先把 ONT 的 LAN 保持在独立网段（只接终端），断开回到主猫 LAN 的冗余铜线；再判断协议层。临时止血可以先把该 `fttrN` 从网桥摘下，但要记录并恢复。

## 8. 常见误判清单

- O5、profile 回读成功、UI 的 verified 都不等于当前双向转发。
- 拿到一次 DHCP 不等于稳定：可能只覆盖 carrier 上升后的十几秒。
- 结果码 9 不等于实体不存在；结果码 7 不等于只能重试。
- 累计计数、其他 ONU 的 MAC、OMCI 包都不能当作目标业务报文证据。
- ONU 静默不等于不存在：它可能只是没有流量可发；先制造可控刺激（ARP/DHCP/从管理口 ping）再判定。
